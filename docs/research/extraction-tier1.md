# Deterministic PDF Extraction (Tier 1)

## Bottom line

- Tier 1 is a **text-and-geometry recovery layer, not a document parser**. Every candidate library returns positioned glyph runs; reading order, columns, paragraphs, headers and tables are all caller responsibilities ([pypdf docs](https://pypdf.readthedocs.io/en/stable/user/extract-text.html), [pdf.js text_layer.js](https://raw.githubusercontent.com/mozilla/pdf.js/master/src/display/text_layer.js)).
- **Split the stack by licence, not by capability**: pdf.js (Apache-2.0, zero runtime deps) in the JS reader; PyMuPDF + pdfplumber on the GPU host. PyMuPDF is AGPL-3.0/commercial and Artifex's own licensing page names the client→server shape as the trigger ([artifex.com/licensing](https://artifex.com/licensing/) — quote verified verbatim). **If AGPL is unacceptable, pypdfium2 (Apache-2.0 *or* BSD-3-Clause, no mandatory runtime deps) is the drop-in server alternative** and scores *higher* than PyMuPDF on both public benchmarks — but it also exposes the most render/extract divergences of any engine tested (22/25, the worst in the panel). See §2.
- **Scientific PDFs are the measured worst case** for every rule-based tool: text F1 0.76–0.85 vs 0.95–0.99 on other genres, and rule-based table detection F1 0.06–0.34 vs 0.91 for a learned detector ([arXiv 2410.09871](https://arxiv.org/html/2410.09871v1)).
- **Loud failures are cheap to detect** (`(cid:N)`, U+FFFD, no text layer, Type-3 fonts, Identity-H without ToUnicode). **Silent failures are not**: a wrong /ToUnicode CMap emits plausible text with no artifact ([arXiv 2606.15020](https://arxiv.org/pdf/2606.15020)).
- **Measured, decisive negative result**: randomising 100% of digits on 414 real academic pages flagged *zero* additional pages under the full text-quality rule set. The classifier is structurally blind to numeric corruption — that failure needs a separate defence.
- Ship classifier: **six structural hard gates (any-of), then five weighted text terms, escalate at score ≥ 2**. Measured 4.6–6.0% false-positive rate on clean academic pages.
- The best single text signal is a **dictionary hit rate over lowercase-initial tokens, threshold 0.85** (6.0% FP vs 22.7% for the all-token variant at the same cut).

**Quality on born-digital PDFs is not the differentiator.** py-pdf/benchmarks (i7-6700HQ, 14 born-digital PDFs, default calls) scores pypdfium2 97%, pypdf 96%, PyMuPDF 96%, Tika 95%, pdftotext 91%, pdfminer.six 89%, pdfplumber 75% — but the metric is a raw `Levenshtein.ratio` against a hand-made text file with **no whitespace normalisation and no reading-order alignment** ([score.py](https://github.com/py-pdf/benchmarks/blob/main/pdf_benchmark/score.py)), so a stray newline costs as much as a wrong digit. It is a layout-agreement score, not a character-accuracy score. pdfplumber's per-document scores are bimodal (98/97/94% on some files, 57–68% on eight others), consistent with systematic line-break differences rather than per-character misreads. (Per-document row verified: 94/84/68/97/61/93/61/89/57/59/67/58/98/67 — three files ≥94%, eight in 57–68%.) **Age condition:** that README's own version table pins PyMuPDF 1.26.1, pdfplumber 0.11.7, pypdfium2 4.30.1, pdfminer.six 20250506, pdftotext 0.86.1, all dated 2024-12 to 2025-06 — i.e. ~14 months stale as of 2026-08-29 and *not* the versions in the table above. The corpus is also 14 arXiv-style PDFs, so it is a scientific-genre benchmark with n=14.

**pypdfium2 is the permissive engine the licence discussion usually forgets.** It ties PyMuPDF for speed (0.1 s/doc), beats it on the py-pdf quality metric (97% vs 96%), and posts the highest rule-based text-extraction F1 on the *scientific* category of DocLayNet — 0.8526 vs PyMuPDF 0.8395, pdfminer.six 0.8510, pdfplumber 0.7644, pypdf 0.7641 ([arXiv 2410.09871 Table 4](https://arxiv.org/html/2410.09871v1), verified). What it costs: no raw object access (so no font-dictionary inspection for the A3 gate — that has to come from another library), and PDFium is documented as not thread-safe, so a service must serialise or process-pool it.

**The cheap high-fidelity primitives.** PyMuPDF's relative-speed table (~2,700 pages, hardware undisclosed, so ratios only) shows `rawdict` costs 4.50× plain text *with* images but only **1.68×** with `TEXT_PRESERVE_IMAGES` cleared; `words` costs 1.02× ([Appendix 1](https://pymupdf.readthedocs.io/en/latest/app1.html)). `get_texttrace()` is documented as "up to twice as fast, compared to 'rawdict'" and returns glyph IDs, `spacewidth`, and a `type` field where 3 = invisible text — the fingerprint of an OCR layer under a scan ([functions](https://pymupdf.readthedocs.io/en/latest/functions.html)). Its contract is the useful part: trace chars "contain no spaces, except the document creator has explicitly coded them. They will never be generated."

**PyMuPDF's tables are pdfplumber's algorithm.** `src/table.py` states verbatim that it was ported from pdfplumber's MIT code and relicensed AGPL, adding only header detection ([table.py](https://raw.githubusercontent.com/pymupdf/PyMuPDF/main/src/table.py)). Choosing PyMuPDF for tables buys speed, not a better algorithm.

### Conflicts

- **Speed ratio.** py-pdf implies PyMuPDF:pdfplumber ≈ 95× on the mean and ~150× on the largest file (i7-6700HQ, 14 born-digital PDFs); pdfmux measures 10× (M1 MBP, 1,422 mixed real-world pages). Both are credible and neither corpus is academic papers. pdfmux also ships a competing MIT extractor. Treat **10–95×** as the honest band and measure on the real corpus.
- **Table accuracy.** pdfmux reports TEDS 0.847 pdfplumber vs 0.692 PyMuPDF on a 200-table subset — surprising given the shared algorithm, published without reproduction code, and independently uncorroborated. Directional only.

## 2. JS-hosted reader vs Python extraction service

**Recommendation: pdf.js in the reader for interactive tier-1 text; PyMuPDF + pdfplumber (+ optional docling) on the GPU host for the batch/escalation path, with pypdfium2 as the drop-in replacement for PyMuPDF the moment the AGPL counterparty question becomes real.** Four reasons, in order of weight.

**Licence.** PyMuPDF is dual AGPL-3.0/commercial and Artifex states the trigger in the exact shape of this architecture: "You cannot deploy our open-source as part of a server-based application or service, without disclosing your own application's full source code under AGPL to any users interacting with it" ([artifex.com/licensing](https://artifex.com/licensing/)). A single-user personal setup has no counterparty for AGPL §13; the moment the reader is distributed or the extraction service serves anyone else, it forces AGPL on the reader or a paid licence (Artifex publishes no price list). pdf.js is Apache-2.0 with **no runtime dependencies** and a `browser` field that stubs out canvas, fs, http, https and url — the text path pulls no native module ([package.json](https://cdn.jsdelivr.net/npm/pdfjs-dist/package.json)). The escape hatch on the server is **pypdfium2, dual Apache-2.0/BSD-3-Clause with no mandatory runtime dependency** ([PyPI](https://pypi.org/project/pypdfium2/)) — permissive, faster-or-equal, and higher-scoring than PyMuPDF on both public benchmarks. Two hidden licence edges to know about: **pdftotext is GPL** (per the py-pdf benchmark's own dependency table), and **`pdfplumber.open(repair=True)` shells out to a Ghostscript binary** it locates with `shutil.which("gs")` ([repair.py](https://raw.githubusercontent.com/jsvine/pdfplumber/stable/pdfplumber/repair.py)) — so the "MIT" label on pdfplumber does not cover the repair path, which needs an AGPL Artifex binary installed.

**Integrity, not just licence.** Liu & Ming ran all 25 extraction gaps against ten dual-capability engines and counted how many produce a render/extract mismatch *within that same engine*. Verified from the paper's Table 2 totals row: **Pdfium 22/25 (worst), MuPDF 19/25, PDF Expert 19/25, PDFBox 18/25, Poppler 17/25, Foxit 16/25, PDF.js 15/25, Xpdf 12/25, GhostScript 11/25, Adobe Acrobat 9/25 (best)**; text pipelines: PyPDF 20/25, PDFMiner 17/25, Unstructured 17/25, Docling 18/25, OpenDataLoader 11/25, LlamaParse 10/25 ([arXiv 2606.15020](https://arxiv.org/pdf/2606.15020), Ubuntu 24.04 / Intel Core Ultra 9 285K / 64 GB, March 2026 measurement window, 25 hand-built canary PDFs — *not* a natural-corpus prevalence estimate). This cuts directly against the speed/licence argument: **the two engines that win on speed, licence and quality (pypdfium2 and PyMuPDF) are the two worst on render/extract consistency**, and pdf.js in the reader sits mid-pack at 15/25. There is no engine that is simultaneously fast, permissive and integrity-clean; the mitigation has to be the cross-engine diff in §5, not engine choice.

**Runtime weight.** pdf.js removes the Python runtime, torch, and the model cache from the client entirely. Docling's PDF path pulls `torch >=2.2.2` plus ~0.5 GB of weights (TableFormer-accurate 203 MiB, layout-heron 164 MiB) and 0.5 GB more for granite-docling-258M ([pyproject](https://raw.githubusercontent.com/docling-project/docling/main/pyproject.toml), [HF](https://huggingface.co/ds4sd/docling-layout-heron)). At 1.26 s/page on an M3 Max it is a batch tool, not something the reader runs while the user waits.

**The cost you pay.** pdf.js gives you no reading order, and its own viewer never needed one — spans sit over the canvas so visual order comes from geometry. Column recovery, hyphen joining, header/footer stripping and caption exclusion are all caller code. Item boundaries are unstable: [#18201](https://github.com/mozilla/pdf.js/issues/18201) documents "Johns" arriving as `"Jo"` + `"hns"` in one PDF while another returns an entire line as one item with no spaces. Word breaks come from fixed multiples of font size in `evaluator.js` — `NOT_A_SPACE_FACTOR 0.03`, `TRACKING_SPACE_FACTOR 0.102`, `SPACE_IN_FLOW_MIN/MAX 0.102/0.6`, `NEGATIVE_SPACE_FACTOR −0.2` — and the PDF Association records that the spec defines no word-boundary heuristic at all: Adobe uses "a dynamic heuristic that weights the length of strings chunks" while pdf.js uses "a comparison with a fixed size" ([pdf-issues #564](https://github.com/pdf-association/pdf-issues/issues/564)). **Do not treat Acrobat copy-paste as ground truth.** (pdfminer's `word_margin=0.1` and pdf.js's 0.102 converged on the same threshold independently.) Mozilla's FAQ grades Node.js 22+ as "Mostly" supported ("Some missing features, but no problems in general") with "Limited" automated testing — **that row is in the *legacy build* support table**, a condition the original phrasing omitted ([FAQ](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions), verified) — run extraction in a renderer/worker and pin the version.

Two pdf.js gotchas that shape the classifier: `getTextContent` documents that "All occurrences of whitespace will be replaced by standard spaces (0x20)", so tables must be found geometrically from `transform[4]`/`width`, never from the string. And `TextContent.styles` carries only `{ascent, descent, vertical, fontFamily}` — **there is no per-font encoding-provenance signal in pdf.js**, so a JS-side broken-encoding check must be a string-pattern scan or a raw font-dictionary parse. (Independently re-verified against `src/display/api.js` on master during this audit: the `TextStyle` typedef at L1194–1199 lists exactly those four properties.)

**The missing angle: marked content and the structure tree.** The dossier's claim that pdf.js "has no reading order at all" is true of `TextItem[]` but incomplete about what pdf.js *exposes*. `getTextContent({includeMarkedContent: true})` interleaves `TextMarkedContent` records — `{type: 'beginMarkedContent' | 'beginMarkedContentProps' | 'endMarkedContent', id}` — into the same items array ([api.js](https://raw.githubusercontent.com/mozilla/pdf.js/master/src/display/api.js) L1149–1189, verified). `TextContent` also carries `lang`, "The document `/Lang` attribute" (L1164) — a free per-document language signal the classifier currently ignores, and the correct gate for whether an English wordlist should be applied at all. On the Python side pdfplumber attaches `mcid` (marked-content section ID) and `tag` (section tag) to **every** char, line, rect, curve and image object, flagged *Experimental* ([README](https://raw.githubusercontent.com/jsvine/pdfplumber/stable/README.md), verified). In a properly tagged PDF the structure tree gives a *declared* reading order and block role, which is strictly better than any geometric heuristic. **What is unverified: how many academic PDFs are actually tagged.** LaTeX/pdfTeX output is historically untagged, and no prevalence figure for arXiv or journal PDFs was retrievable in this audit (see §8). Treat marked content as a signal to *opportunistically use and measure*, not to depend on.

| **Type-3 glyph-name permutation** | Encoding maps codes to glyph names in arbitrary order; page renders "ABC", extractor returns "CAB" — "invisible to any diff-based integrity check" (EG18) | Enumerate page font subtypes; any `/Type3` = hard escalate | Free |
| **CID byte-pair fallback** | Missing descendant `/Type` makes extractors read ASCII bytes in pairs; `53 54 4F 50` renders "STOP", extracts as two CJK ideographs (EG23) | CJK codepoints in an English document | Free |
| **Column interleaving** | Content stream is column-major, layout is row-major → `A→C→E→B→D→F` (EG16) | Extract in content-stream order **and** geometry-sorted order; sequence divergence = column-interleaved page | 2nd extraction |
| **Word run-together** | MuPDF's inter-glyph advance threshold. | **Column merge in tables** | Right-aligned numbers touch left-aligned text within `x_tolerance=3` pt ([#177](https://github.com/jsvine/pdfplumber/issues/177), [#66](https://github.com/jsvine/pdfplumber/issues/66) → "PAYPALPOSDEBIT") | Use `x_tolerance_ratio` so the gap scales with font size | Cheap |
| **Borderless table** | Booktabs rules only; rule-based detection needs "clear boundaries" and fixed column spacing ([2410.09871](https://arxiv.org/html/2410.09871v1)) | Run `lines` and `text` strategies; lines finds nothing but text finds ≥3 columns × ≥3 rows | 1 table pass |
| **Math** | Sub/superscripts extracted as separate lines because "they did not share the same baseline" ([Bast & Korzen](https://ad-publications.cs.uni-freiburg.de/benchmark.pdf)) | Math-font glyph fraction (CMMI/CMSY/CMEX/MSAM/MSBM); baseline deviation > ~15% of line height | Cheap |
| **Fake bold by overprint** | Same glyph drawn twice offset; doubles every letter | `page.dedupe_chars(tolerance=1, extra_attrs=("fontname","size"))` | Cheap |
| **Memory blowup** | "we have seen 10 GB RAM being required" for one page ([pypdf](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)) | Hard per-page memory guard + fallback | — |

**Negative result worth internalising:** rendering the page does *not* immunise a pipeline. Over the 25-gap catalogue (25 hand-built canary PDFs, Ubuntu 24.04 / Core Ultra 9 285K, March 2026), Docling scores 18/25 and Unstructured 17/25 — worse than PDFMiner (17/25) and near PyPDF (20/25). Adobe Acrobat's low 9/25 is partly *dropout*, which the authors classify as an availability failure, not correctness: "several CID font-decoding canaries fail during text export rather than returning render-aligned text." One commercial platform silently fell back to text extraction above an internal page count: 1-, 40- and 80-page variants stayed at 0/25, a 120-page variant exposed 21/25 ([2606.15020](https://arxiv.org/pdf/2606.15020), all figures re-verified against the paper's Table 2 totals row during this audit). **An escalation path that can silently degrade under load is not a safety property.**

Two further specifics from the same paper that bear on the design. (a) The discovery funnel is the honest cost model for cross-engine diffing: 154 variant groups showed implementation-level divergence, but only **72** diverged in *extracted text* — the rest were render-only, and only text divergence can poison a downstream reader. (b) Type-3 permutation severity is construction-dependent, not categorical: **EG24 is exposed by 9/10 engines while EG18 is exposed by only 2/10**, both being Type-3 fallback cases. So the A3 hard gate on `/Type3` is deliberately conservative — it escalates a font class whose *actual* corruption rate varies by an order of magnitude with how the PDF was built, and the paper offers no natural-corpus prevalence for either.

## 4. Dehyphenation and normalization

**Safe, unconditional:** NFKC. Unicode's FAQ says the U+FB01–FB04 presentation forms exist only for legacy round-tripping — "Their use is discouraged. No more will be encoded in any circumstances" ([Unicode](https://www.unicode.org/faq/ligature_digraph.html)) — and as compatibility characters they decompose under NFKC. pdf.js already does this in the worker: `normalizeUnicode()` in `shared/util.js` applies `.normalize("NFKC")` to a targeted regex covering `ﬀ-ﬄ`, `ﬆ`, Arabic presentation forms (`ﬠ`–`﻽` ranges), ` `, `µ`, ` - `, ` ` and `Ω`, with `ﬅ` split out into an explicit map `"ﬅ" → "ſt"`; on unless `disableNormalization: true`. (Re-verified against `src/shared/util.js` L1052–1067 on master during this audit.)

**Trap the classifier must handle, found in that regex.** `ﬅ` (U+FB05) is mapped to **`ſt` — U+017F LATIN SMALL LETTER LONG S followed by `t`** — which is what NFKD/NFKC actually specify, so pdf.js is correct. But U+017F appears in no modern English wordlist: `dwyl/english-words` is ASCII-only, so every word that came through a `ﬅ` ligature (`ſtate`, `firſt` in older typesetting, and any modern font that emits U+FB05) is a guaranteed dictionary miss. The same holds for anything NFKC leaves as a non-ASCII letter. **B1's dictionary lookup must fold U+017F→`s` (and NFD-strip combining marks) before the lookup, or long-s pages will false-positive.** This is an extractor-specific normalisation step, which is exactly the class of thing §7 item 3 says must be recalibrated per extractor — PyMuPDF with `TEXT_PRESERVE_LIGATURES` cleared and pdf.js with `normalizeUnicode` produce *different* post-normalisation alphabets for the same page. pdfplumber exposes `open(..., unicode_norm="NFKC")` (default unset). PyMuPDF has `TEXT_PRESERVE_LIGATURES` (1) **on by default**, so ligatures survive unless cleared. Not doing this costs accuracy: tools that fail to expand ligatures/diacritics score W~ (misspelled words) of 154 (4.7%), 110 (3.3%) and 149 (4.2%) against 21 (0.6%) for the best tool, over 12,098 arXiv articles ([Bast & Korzen, JCDL'17](https://ad-publications.cs.uni-freiburg.de/benchmark.pdf) — 9 years old; taxonomy corroborated by 2024–2026 work, constants not).

**The hyphen decision has a ceiling and a named trap.** A line-final hyphen is either a soft break (merge) or a mandatory compound hyphen (keep). Measured balanced accuracy on ClueWeb12 Extract: vocabulary baseline 66.87%, word-level logistic regression 92.38%, character-level bi-LSTM 90.14%, with an explicit trade-off between recognising naturally-hyphenated words and merging correctly ([Hernæs 2019](https://ad-publications.cs.uni-freiburg.de/theses/Bachelor_Mari_Hernaes_2019.pdf)). A plain dictionary over 4,987,829 words harvested from 1,106,572 arXiv text files gives 86%, at 0.016–0.048 ms/word in-memory ([Corraya 2018](https://ad-publications.informatik.uni-freiburg.de/theses/Master_Sumitra_Corraya_2018.pdf)). The trap is documented in the benchmark's own residual-error list: "*Compound words with mandatory hyphens (like sugar-free)… In most cases, Icecite handles them as normal hyphenated words and removes the hyphen mistakenly (merges sugar-free to sugarfree)*."

**Design consequence:** a line-final hyphen is *not* an escalation trigger. It is a local ~90%-solvable repair whose residual is a word-level error, not a numeric one. PyMuPDF's `TEXT_DEHYPHENATE` (16) exists but is only in `TEXTFLAGS_SEARCH`, never in an extraction default — enable it deliberately or do the join yourself with a dictionary check.

**Traps.** (a) `pdfminer.word_margin` default 0.1 is a known source of *spurious* spaces; users report needing 1.0. Real pdftotext output on arXiv shows **2,355 spurious spaces vs 594 missing** across 10,000 sequences, 12.7% of which contain a tokenization error ([arXiv 2010.07878](https://arxiv.org/pdf/2010.07878v2)) — the classic "run-together" signature targets the *minority* failure. (b) `expand_ligatures=True` is pdfplumber's `extract_words` default, so char count and word-char count legitimately differ. (c) Any threshold calibrated on one extractor's whitespace behaviour is invalid for another; record extractor + parameters alongside every score.

## 5. The escalation classifier

All thresholds below marked **[M]** were measured on 414–432 body pages (>1500 chars) from 24 born-digital academic PDFs (psycholinguistics journals, one- and two-column; arXiv CS), text via PyMuPDF 1.28.2 `page.get_text()`, wordlist [dwyl/english-words](https://raw.githubusercontent.com/dwyl/english-words/master/words_alpha.txt) (370,105 entries), against four synthetic corruption models. Synthetic corruption applied to already-clean text makes these **optimistic upper bounds on separability**.

### Stage A — structural hard gates (any-of → escalate, no scoring)

| Gate | Rule | Grounding |
|---|---|---|
| A1 `no_text` | < 100 chars whose bboxes intersect the interior box (page inset 12.5%/dim) | CCpdf's >100-visible-character floor ([arXiv 2304.14953](https://arxiv.org/pdf/2304.14953)); `margin_ratio = 0.125` from [ocrmypdf info.py](https://raw.githubusercontent.com/ocrmypdf/OCRmyPDF/main/src/ocrmypdf/pdfinfo/info.py). **[M]** clean p01 = 444 chars, p05 = 993 → 4× margin |
| A2 `scanned` | bitmap coverage > 0.75 **AND** interior chars < 500 | `BITMAP_COVERAGE_TRESHOLD = 0.75` in [docling v2.15](https://raw.githubusercontent.com/docling-project/docling/v2.15.0/docling/models/base_ocr_model.py) — verified, and note docling computes coverage as the area fraction of the **union** of bitmap rects rasterised into a 1-bit image, so overlapping images do not double-count. Second published constant for the same job: marker's `image_threshold = 0.65`, "the minimum coverage ratio of the image to the page to consider skipping the page" ([providers/pdf.py](https://raw.githubusercontent.com/datalab-to/marker/master/marker/providers/pdf.py), verified). **Grounding correction:** the earlier claim that the char conjunct is what prevents CCpdf's 15 errors reverses the source. CCpdf's 15 errors were *precision* errors — documents wrongly classified as born-digital-needing-no-OCR — and the paper attributes all 15 to "adding a background with logo text to the file", proposing background metadata extraction as the fix ([2304.14953](https://arxiv.org/pdf/2304.14953) §3.7, verified). That is **under**-escalation, not over-escalation. The 500-char conjunct is defensible engineering but CCpdf is not evidence for it |
| A3 `broken_encoding` | any used font is Identity-H/V without ToUnicode, or Type-3 only | [pdf-inspector detector.rs](https://raw.githubusercontent.com/firecrawl/pdf-inspector/main/src/detector.rs) `has_identity_h_no_tounicode`/`has_only_type3_fonts`; Type-3 permutation is undetectable downstream (EG18) |
| A4 `replacement_chars` | count(U+FFFD) + count(`(cid:NNN)`) > 2 | **[M]** exactly 0 across all 430 clean pages. Far tighter than marker's `max(6, 3%)`, which needs 138 bad chars on a median 4,612-char page |
| A5 `vector_text` | `path_ops ≥ 1000 AND path_ops > 200×text_ops AND unique_alnum < 30` | verbatim from pdf-inspector |
| A6 `too_complex` | `graphics_ops > 10,000 AND graphics/text ratio > 20` | constants from `is_pdf_too_complex(max_graphics_ops=10_000, min_graphics_to_text_ratio=20.0)` in [unstructured pdf.py](https://raw.githubusercontent.com/Unstructured-IO/unstructured/main/unstructured/partition/pdf.py) L637–860, verified. **Not verbatim, and the difference matters:** upstream counts operators with a regex over the *raw content stream*, guards the check behind four more size gates (`min_file_size_bytes`, `min/max_raw_stream_bytes`, `max_content_stream_array_entries = 10_000`, `max_total_stream_bytes`), and returns `True` for the **whole document** if *any* page trips — reusing it per page is our change, not theirs |

### Stage B — weighted text-quality terms (escalate at score ≥ 2)

| Term | Rule | Weight | **[M]** FP on clean | **[M]** detection |
|---|---|---|---|---|
| B1 `dict_low` | dictionary hit rate over **lowercase-initial** alpha tokens (len ≥ 3) < 0.85 | 2 | 6.0% | 100% of 5% letter-substitution |
| B2 `runtogether` | fraction of whitespace chunks > 15 chars > 0.03 | 2 | 1.2% | 93% of 25% space loss; 100% of total loss |
| B3 `oversplit` | fraction of alphabetic chunks of len ≤ 2 > 0.23 | 2 | 0.5% | 71.5% of 5% oversplit; 97.3% of 10% |
| B4 `wordlen_odd` | mean alpha-token length outside [4.8, 7.5] (two-sided) | 1 | 0.0% | 28% of 25% space loss; 100% of total |
| B5 `lowalnum` | alphanum ratio < 0.80, **after collapsing leader runs** (below) | 1 | 0.7% | 14.3% of heavy U+FFFD |
| B6 `garbage` *(candidate, unmeasured)* | fraction of tokens matching any Taghva/Kulp garbage rule > *calibrated cut* | 1 | not measured | not measured |

**B5 has a documented false-positive class, and marker already shipped the fix.** Current marker applies `re.sub(r"(?:[.·•…_\-]\s*){3,}", " ", text)` *before* the ratio checks, with the comment: leader runs "are legitimate typography, not garbled OCR, but their low alphanumeric density otherwise trips the heuristic and forces clean pages (e.g. tables of contents) into needless full-page OCR" ([providers/pdf.py](https://raw.githubusercontent.com/datalab-to/marker/master/marker/providers/pdf.py) `detect_bad_ocr`, verified). Our academic corpus has few dot-leader TOCs, which is plausibly *why* B5 measured only 0.7% FP — the clean set may simply not contain the failure class. **Apply the collapse anyway; it costs one regex and removes a known FP mode the measurement could not see.**

**B6 is a sourced, cheap term the original draft omitted.** Cuper's `garbage` measure is a token-level rule set from Taghva et al. (2001) and Kulp & Kontostathis (2007), listed verbatim in the paper: a token >20 characters; >3 identical characters in a row; vowel/consonant ratio skewed 8:1 either way; more than two punctuation characters after stripping the first and last letter; a token that starts and ends lower-case with an upper-case letter in between; and (their own addition) starting or ending with more than 4 consonants ([JDHB vol 4](https://journal.dhbenelux.org/wp-content/uploads/2022/07/jdhbenelux4_07-Cuper.pdf) §3.2.6, verified). The reference value on their corpus is **0.08** and was stable at 0.08 across full / 25% / 2.5% training data. Two conditions before adopting it: it was calibrated on 17th-century Dutch OCR, and two of the rules (mixed-case interior, consonant runs) will fire on chemical formulae, gene symbols and LaTeX-derived identifiers in scientific text. Calibrate the cut on our own clean pages, per §7.

Restricting B1 to lowercase-initial tokens is the single largest cheap win: it drops proper nouns, acronyms, sentence-initial words and citation surnames, moving the clean p10 from 0.800 → 0.883 and the FP rate from **22.7% → 6.0%** at the same 0.85 cut, with detection unchanged. Signals are near-orthogonal — each corruption mode is caught by exactly one term — which is why the rule is a decision list, not a single score. The any-of over six terms measures 4.6% FP with 95.2% / 100% / 47.1% / 100% / 100% / 89.1% / 100% detection across the modes.

**Deliberately excluded.** Non-ASCII ratio: **[M]** median 0.14%, p90 0.58%, p99 1.9%, max 13.0% on a Greek-heavy math page — any threshold catching mojibake also catches real mathematics. Column count: **[M]** per-page left-edge histogram is only 80–87% accurate (over-counts from table columns and caption blocks; under-counts on figure-dominated pages), so use it to pick a reading-order strategy and as a low-weight consistency check against the document's modal count, never as an escalation trigger on its own. PDFBoT's fix is to aggregate the histogram over every page and require peaks of comparable height with a 144 pt (1.5 in) minimum column width ([arXiv 2010.12647](https://arxiv.org/pdf/2010.12647)).

### Cross-engine differential extraction (the only silent-corruption detector)

Liu & Ming's own discovery pipeline is the detector you want: run two engines, "retain a group when at least two engines produce distinct outputs: visibly distinct rendered images or different normalized text hashes after excluding whitespace-only differences." Pick engines with maximally different exposure vectors. From the verified totals row, the widest spread available among engines we would realistically run is **Adobe Acrobat 9/25 / GhostScript 11/25 / Xpdf 12/25 at the clean end vs Pdfium 22/25 and MuPDF 19/25 at the exposed end**; pdf.js sits at 15/25 and PyPDF at 20/25. Note this means the *cheap* pair — PyMuPDF + pypdfium2, both fast, both already installed — is close to the **worst** possible choice for a differential (19 and 22), because they are the two most divergent engines and will disagree with the rendered page in overlapping ways. A PyMuPDF-vs-Poppler(17)/Xpdf(12) diff is the better-grounded pairing.

**Attribution correction.** The earlier draft used a quote from [#2755](https://github.com/pymupdf/PyMuPDF/issues/2755) — "for files where one messes up badly, the other one does well" — to justify pairing PyMuPDF with pdfplumber. Re-reading the thread, that comparison is **PyMuPDF vs pypdf**, not pdfplumber, so the quote does not support that pairing. The structural argument for PyMuPDF + pdfplumber still stands on its own (MuPDF synthesises spaces in C from font metrics; pdfplumber applies one arithmetic rule in Python over pdfminer.six chars with no synthesis) but it is now an **unverified engineering judgement**, not a cited one. Run the diff only on table-flagged pages to bound the cost — and note from §3 that only ~47% of Liu & Ming's divergent groups (72 of 154) diverged in *text* at all, so a render-plus-text diff spends roughly half its work on divergences that cannot affect the reader.

### Per-page output

```json
{"page": 12, "escalate": true, "score": 2,
 "reasons": ["dict_low", "numeric_unverified"],
 "signals": {"chars_interior": 3811, "bitmap_coverage": 0.02,

   "replacement_chars": 0, "column_count": 2, "doc_modal_column_count": 2,
```

`doc_lang` comes free from `TextContent.lang` (`/Lang`) in pdf.js and from the catalog in any Python engine; **B1 must be skipped, not failed, when `doc_lang` is absent or non-English** — otherwise every non-English page escalates as `dict_low`, which is a 100% false-positive rate on a document class the classifier never measured. `has_marked_content` records whether `mcid`/`tag` (pdfplumber) or `TextMarkedContent` (pdf.js) were present, so the golden-set calibration can answer the §8 prevalence question as a by-product rather than as a separate study.
The reason vocabulary extends pdf-inspector's four codes (`no_text`, `scanned`, `vector_text`, `suspected_garbled_text`) with the stage-B codes plus `too_complex` and `numeric_unverified`. **Carrying raw signal values, not just booleans, is what makes threshold re-calibration possible without re-parsing every PDF.**

### Conflicts

- **Dictionary threshold.** Cuper et al. derive 84.6% (token) / 83.3% (type) as the 90%-inclusion cut on 17th-century Dutch newspaper *sentences* ([JDHB vol 4](https://journal.dhbenelux.org/wp-content/uploads/2022/07/jdhbenelux4_07-Cuper.pdf)); literature elsewhere uses a flat 80%. **[M]** on academic English *pages*, the all-token p10 is 0.800 and 0.85 would escalate 22.7% of clean pages. The lowercase-only variant reconciles them. Use Cuper's *procedure* (percentile of your own clean corpus), not their constant.
- **marker's `alphanum_ratio < 0.3`.** **[M]** it fired on 0% of every corruption mode tested and sits 0.5 below the worst clean academic page — effectively dead code outside symbol soup. B5 raises it to 0.80.
- **docling's `bitmap_area_threshold`.** Maintainer discussion says 0.75; the v2.15.0 source says `bitmap_area_threshold: float = 0.05` for a *single* bitmap, with 0.75 a separate local constant for *total* coverage. Trust the source; copying 0.75 from prose builds the wrong per-bitmap filter. Verified precisely this audit: the actual test is `coverage > max(BITMAP_COVERAGE_TRESHOLD, self.options.bitmap_area_threshold)` — a `max()`, so raising the per-bitmap option above 0.75 silently raises the full-page threshold too.
- **Word-length band.** B4 uses `[4.8, 7.5]` measured on English academic pages; Cuper's equivalent reference band is **`[4.15, 6.25]`** for 17th-century Dutch sentences, stable to `[4.17, 6.21]` at 2.5% of training data (Table 5 / Table 9, verified). Both are corpus artefacts, not language universals — the ~0.7-word gap is the size of the error you inherit by borrowing someone else's band. Cross-corpus reuse of B4 is not defensible; the procedure is.
- **Two independent published thresholds for "page is mostly image".** docling 0.75 (union area of bitmap rects) vs marker 0.65 (single image / page area). Both verified in source, neither justified in either repo. A2's 0.75 is a choice between them, not a consensus.

**Corrected finding: heuristics were *supplemented*, not abandoned — and the supplement is specifiable.** The previous draft claimed two projects replaced their heuristics with models. Only docling did. Verified on `main`: `BITMAP_COVERAGE_TRESHOLD` is gone from `base_ocr_model.py`, `OcrMode.DEFAULT` is wired to `PDF_AWARE_LAYOUT_REGIONS`, and the routine is documented in the source as:

> 1. Start from the layout clusters. 2. Eliminate clusters that intersect exclusively with programmatic text PDF cells. The following clusters therefore remain: clusters without any overlapping PDF cell; clusters with at least one overlapping non-text region (e.g. bitmap, shape). 3. Deduplicate the remaining cluster bboxes.
> — [`_find_pdf_aware_layout_ocr_rects`](https://raw.githubusercontent.com/docling-project/docling/main/docling/models/base_ocr_model.py), with `DEFAULT_DILATION_SIZE = 20` on the dedup step

marker, by contrast, still runs `detect_bad_ocr` with the identical 0.7/0.6/0.3/`max(6,3%)` constants on master; its model-based check (`detected_line_coverage`) was already there in v0.3.10 and sits *alongside* the heuristic, not in place of it. So the honest reading is weaker than "the heuristic ceiling forced a model" and more useful: **a cheap layout model buys you *region-level* routing, which no text statistic can give you, while the text heuristics stay in place because they are still the only thing that catches garbled-but-present text.**

**And the docling rule has a flaw that matters for academic pages.** Read step 2 carefully: a cluster is kept for OCR if it has *any* overlapping non-text content, **even when it also contains perfectly good programmatic text**. On a paper page, every figure-with-caption and every ruled table trips that branch. That is a deliberate recall-over-precision choice for a general document converter; for our corpus it would escalate most body pages. Adopt the *shape* (layout clusters × parser-coverage per region), not the branch order.

A layout-model-plus-coverage check remains a serious tier-1.5 candidate on the MacBook before touching the GPU — but it is a new implementation, not a copy.

**Three landmines.** docling's `table_score` is declared but **never computed** (`np.nan`) — verified in [base_models.py](https://raw.githubusercontent.com/docling-project/docling/main/docling/datamodel/base_models.py), where all four of `parse_score`/`layout_score`/`table_score`/`ocr_score` default to `np.nan`, `mean_score` is `np.nanmean` over the four and `low_score` is `np.nanquantile(..., q=0.05)` over the four — so an uncomputed sub-score silently drops out rather than penalising, and **the grade tells you nothing about tables** ([confidence scores](https://docling-project.github.io/docling/concepts/confidence_scores/)). (Note the two different quantiles: `parse_score` itself is the **0.10** quantile over per-cell `rate_text_quality` values, with the source comment "To emphasise problems in the parse_score, we take the 10% percentile score of all text cells"; the document-level `low_score` is the **0.05** quantile over the four sub-scores. Do not conflate them.) CCpdf's `image_count == 0` would escalate every academic page bearing a figure; its measured **recall is 43.31%** against a gold standard in which 471/967 (48.71%) documents were born-digital-no-OCR and another 321/967 (33.20%) were "born digital, OCR required" — text-layer presence is a demonstrably inadequate gate, and the classifier it produces is high-precision/low-recall by construction. pdf-inspector defaults to `ScanStrategy::Sample(8)` (verified in [detector.rs](https://raw.githubusercontent.com/firecrawl/pdf-inspector/main/src/detector.rs)), so per-page routing means scanning every page; its quoted ~10–50 ms is for the sampled configuration.

**Do not build the rule as a conjunction.** QuPipe requires every measure to pass and measures recall of 0.008 (modern dictionary) to 0.142 (combined dictionary); a single 80% token dictionary lookup on the combined dictionary scores **precision 0.818, recall 0.470** — beating the full pipeline's 0.906/0.142 on recall by 3.3× for 0.09 of precision (verified against [Cuper Table 6](https://journal.dhbenelux.org/wp-content/uploads/2022/07/jdhbenelux4_07-Cuper.pdf); conditions: 17th-century Dutch newspaper OCR, sentence-level, CER-derived good/not-good labels). Their own "smart quantity" relaxation recovers recall to 0.418 by dropping the sentence-length measure — i.e. the fix for a conjunction is to delete terms, which is the argument for §5's any-of decision list.

## 7. What must be calibrated on the golden set

1. **All five stage-B thresholds**, by Cuper's procedure — order the measure over clean pages, take the 10th-percentile cut. Their Table 9 shows reference values are stable from just 2.5% of the ground truth (~1,890 sentences: token lookup 84.6% → 84.4%, garbage 0.08 → 0.08), so a few hundred golden pages suffice.
2. **A2's 500-char conjunct and A4's threshold of 2** — engineering estimates, not measured against real full-bleed-background pages.
3. **Per-extractor recalibration.** Every whitespace-derived threshold (B2, B3, B4) is a property of the extractor's space heuristic. pdf.js at 0.102×fontSize, pdfminer at `word_margin=0.1`, MuPDF's C heuristic and pdfplumber's `x_tolerance=3` produce different chunk distributions on identical input. Calibrate once per extractor configuration and record which produced each score.
4. **Escalation rate, and therefore GPU cost.** No published base rate exists for Identity-H-without-ToUnicode or broken encodings in modern arXiv/journal PDFs; Liu & Ming's exposure counts are against adversarial canaries, not prevalence. A one-off A3 scan over a few thousand corpus PDFs settles it cheaply and locally.
5. **The 10× vs 95× speed question**, by timing both libraries on ~200 pages of the actual corpus on the actual MacBook. Neither published corpus is academic papers.
6. **The `synthetic` and `TEXT_SEGMENT` semantics** (§8) — one-page empirical checks that unlock real classifier features.
7. **Genuinely broken pages.** Synthetic corruption is *uniform random*; real ToUnicode failures are *correlated* — a whole font breaks, so whole runs break together. 30–50 real broken academic pages with known-correct text is the highest-value collection task.
8. **A caption-vs-column control set**: 13–19% of two-column pages produced 3- or 4-peak histograms, unlabelled as to figure captions vs table columns.
9. **Marked-content / tagged-PDF prevalence on the actual corpus.** Cheap to measure and it changes the design: count pages where pdfplumber returns a non-`None` `mcid`/`tag` on ≥1 char, and documents with a `/StructTreeRoot`. If prevalence is high, reading order is a lookup, not a heuristic; if it is near zero (the expected result for pdfTeX output), close the question and stop considering it. No published prevalence figure was retrievable in this audit.
10. **`doc_lang` coverage and the non-English base rate.** B1 is undefined for non-English pages and will fire at ~100% on them. Measure how many corpus pages carry a usable `/Lang` and how many are non-English before shipping B1 unguarded.
11. **B6 (`garbage`) has no measurement at all.** Cuper's 0.08 reference is 17th-century Dutch. Run the six rules over the same 414–432 clean pages that produced B1–B5 and take the same 10th-percentile cut, then re-test against the four synthetic corruption modes. Until then B6 is a proposal, not a term.
12. **Cross-engine differential cost and pairing.** §5 now argues PyMuPDF+pypdfium2 is a poor differential pair (19/25 and 22/25 exposure) and PyMuPDF+Poppler/Xpdf better. That is reasoning from a canary benchmark, not from our corpus. Measure actual disagreement rate on ~200 real pages per candidate pair before committing — a pair that disagrees on 30% of clean pages is useless whatever its canary score.

The specific mechanics — comparing page *i* against *i*±2 to survive verso/recto alternation, the fuzzy-match edit-distance threshold, reported accuracy — are **UNVERIFIED**. This audit's WebSearch budget was exhausted before this question could be searched (WebFetch-only from that point), so absence of a source here reflects the audit's constraint, not a literature gap.
- **`pdftotext` is GPL** per py-pdf/benchmarks' dependency table, and pdfplumber's repair path requires an Artifex Ghostscript binary. Neither was in the original licence analysis. Whether either matters depends on the same distribution question as PyMuPDF — **unresolved because the deployment shape is not yet decided.**
- **No published per-page escalation classifier exists.** Every benchmark retrieved evaluates whole tools on whole corpora. The stage A/B combination above is assembled from primary sources about individual failure modes; **the combination itself is unsourced and has no published calibration.**
- **Numeric fidelity is not defended by any of this.** Digit substitution preserves token length, whitespace structure, alphanumeric ratio and character-class distribution exactly, so no text statistic can see it. The defence must be a separate mechanism: cross-engine digit-span diffing, unconditional escalation of detected table regions, or reconciliation against a re-render. Emit `numeric_unverified` for any page containing digits rather than implying the classifier checked them.

### What remains genuinely unresolved

Everything already listed in §8 stands, minus the reversed pdfplumber entry. The three that most constrain the design:

1. **Numeric fidelity still has no detector.** Nothing found in this audit changes §8's conclusion: digit substitution is invariant under every text statistic the classifier computes, and neither cross-engine diffing nor `glyph_id` has any published detection rate for it. `numeric_unverified` remains an admission, not a mitigation.
2. **Every escalation-rate estimate is still unanchored to a real corpus.** Liu & Ming give exposure counts on 25 hand-built canaries; CCpdf gives a document-level base rate over a web crawl; neither answers "what fraction of *our* pages are broken". The classifier's FP rates are measured against synthetic corruption of already-clean text, which §5 correctly calls an optimistic upper bound. §7 item 7 — 30–50 genuinely broken academic pages with known-correct text — remains the highest-value collection task and nothing in this audit substituted for it.
3. **The stage A/B combination is still unsourced as a combination.** Every constant now traces to a retrieved primary source, and several of those sources *disagree with each other*: 0.65 vs 0.75 for image coverage, 4.15–6.25 vs 4.8–7.5 for mean word length, 0.3 vs 0.80 for alphanumeric ratio. No published work combines per-page signals this way or reports a calibration for doing so. This audit improved the provenance of the parts; it did not validate the whole.
